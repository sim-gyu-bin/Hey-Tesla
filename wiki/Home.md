# Hey Tesla Wiki

잠긴 휴대폰을 주머니에서 꺼내지 않고 차량에 접근해 음성으로 프렁크 개방을 요청하는 **Android 네이티브 앱**의 제품·기술 문서다.

> 현재 **소스·생성 APK·S23 설치본은 `0.66.0`(`versionCode=66`)·서비스 OFF**다. [v66 좌표 안내](Tesla-Integration.md#v66-좌표-기반-나침반uwb-병행)는 BLE 차량 좌표와 휴대전화 위치·진북으로 대략적 거리·방향을 계산하고 UWB 실측과 구분한다. 호스트·실기기 FGS/source·UI 검증과 데이터 보존 설치를 마쳤다. 실제 차량 위치 응답·UWB 거리 수신 성공은 미검증이다. [검증 기록](Device-Validation.md)을 따른다.
>
> [UI 개편 기록](UI-Design.md)과 프로젝트 전용 [hey-tesla-ui 스킬](../.omp/skills/hey-tesla-ui/SKILL.md)에 따라 **홈 → 설정 → 개발자 진단**을 분리했다. 홈 ON은 v55부터 **차량 감지 → 기존 앱 키 인증·FiRa → 자동 UWB·알림** 제품 경로다. 직접 차량 감지는 사용자 검증 완료지만 실차 UWB 거리·각도는 아직 미수신이며, 자동 마이크·호출어·프렁크는 미연결이다. 별도 명시 승인으로 시작하는 수동 음성 프렁크 구현은 유지한다.

## 핵심 결정

- Android 앱은 **Kotlin + Jetpack Compose**로 개발한다. React Native, Android 앱의 TypeScript 로직, JavaScript 브리지는 사용하지 않는다.
- 서비스·Bluetooth·오디오 수명뿐 아니라 명령 해석, 상태 머신, 설정, 게이트웨이, 앱 테스트도 Kotlin으로 통일한다.
- 초기 산출물은 실제 Tesla 제어가 없는 **Android 기술 검증 앱**이었다. 현재는 자동 UWB와 별도 승인 수동 음성 프렁크까지 구현했지만, 초기 설정 후 잠금·주머니·차량 접근·무터치 마이크 및 자동 제어 목표는 아직 미통과다.
- 기본 음성 비서로 선택된 `VoiceInteractionService`와 저전력 접근 신호를 조합한 경로를 우선 시험한다. 네이티브 전환이나 기본 비서 지정만으로 Android 제약이 해소된다고 가정하지 않는다.
- mock/dry-run 음성 진단은 차량 미전송 경로로 분리한다. 실제 명령은 별도 명시적 승인의 수동 음성 프렁크 하나로 제한하며 실차 실패를 mock 성공으로 대체하지 않는다.
- 차량 키는 앱 전용 AndroidKeyStore에서 생성·재사용하며 BLE 등록 요청을 사용자가 키카드·차량 화면에서 승인한다. 공식 앱 폰키를 가져오거나 API에서 개인키를 발급받지 않는다. Fleet API/OAuth·서버·도메인·결제는 필요성과 승인 확인 후 선택하며 BLE의 선행 조건이 아니다.
- v21 앱 키 인증·암호 조회·재연결, v24 P UI 관측, v25 및 v27 광고명 감지 기록은 각 버전의 역사적 검증이다. 직접 감지의 사용자 검증과 현재 자동 UWB 구현을 구분한다. UWB는 기존 키·BLE/OOB 합의 뒤 정밀 거리 단계이며 **지원 조회만 있는 상태가 아니다**. v59는 연결 중 종료, v60은 인증 뒤 로컬 ID 검사에서 종료됐다. v61 실차1회는 인증·capabilities 송신·notification12 뒤 협상30초 기한이 만료됐고 request 처리·RF·거리/각도는 미관측이다. v62는 원인 확정 없이 보안·수락 정책을 바꾸지 않고 수신 관측을 보강한다. UWB를 수동 BLE 프렁크의 필수 조건으로 만들지 않는다. 별도 수동 음성 프렁크도 신선한 P·명시 승인·인식기 정리 확인·단발 전송·ACK와 후속 BODY 분리를 요구하며 실제 개방은 미검증이다. [요구사항](Requirements.md#차량-연동-개발-기준)을 따른다.

## 단계별 개발 순서와 진행 조건

승인된 전체 흐름과 통과 기준은 [18단계 구현 계획](Implementation-Plan.md)이 기준이다. 사용자는 6단계 실차 시험을 대기 상태로 두고 독립적인 **7단계 엔진 비교·지원 조회·수동 STT·PCM 진단과 TTS 파일 무음 시험**을 먼저 진행하도록 승인했다. 발화·화면 조작 참여를 최소화하도록 합성 파일·대조·자동화 시험을 우선한다. 이는 6단계 합격이나 최종 음성 엔진 확정을 의미하지 않는다.

| 단계 묶음 | 산출물 | 다음 단계로 넘어가는 조건 | 현재 상태 |
| --- | --- | --- | --- |
| 1~6. 환경·검증 앱·접근·제한 세션 | 호환 환경, 진단, 실제 접근 후보, 제한 오디오 세션, 잠금·주머니 무터치 시험 | 실제 잠금·접근·입력·종료 기록 | 직접 차량 감지 사용자 검증 완료. 자동 UWB 구현·실차 거리 미수신. 자동 마이크 결합과 6단계 전체는 미통과 |
| 7~11. 음성·dry-run | 온디바이스 한국어 처리, 파서, 상태 머신, dry-run과 TTS 종료 | 연속 발화·안전 거절·자원 해제 기록 | 수동·파일 진단과 dry-run 통합 구현·실측. 잠금·주머니 자동 접근 결합·제품 전체 합격은 별도 |
| 12~15. 로컬 BLE Tesla 연동 | 앱 자체 키·사용자 카드 승인·인증·키 재사용·안전 상태·수동 프렁크 | 암호 상태 수신·키 재사용과 신선한 P·차량 감지, 별도 승인 실차 명령·물리 결과 | v21 인증·암호 조회·같은 키 재연결, v24 P UI 관측, 직접 감지 검증은 각각의 근거로 보존. 별도 승인 수동 음성 프렁크 구현 유지·실제 개방 미검증. Fleet 분기는 선택 |
| 16~18. 강건성·개인용 배포 | 실패·장기 대기·복구·설치 및 해제 절차 | 실제 측정 범위와 실패 기록 | 미착수 |

1~6단계 합격 전에도 독립적인 음성 진단과 사용자 요청의 UI 조사·프로젝트 스킬·개편안은 진행할 수 있다. UI의 개선을 자동 접근·음성 엔진·실차 제어 합격으로 대체하지 않는다. 대규모 서버·추가 차량 명령은 현재 범위 밖이며, 배터리·지연 수치는 실제 측정 전 약속하지 않는다.

### 실패 시 처리

- 적합한 접근 신호가 없거나 마이크 시작이 공식 권한 범위에서 불가능하면, 어떤 조건이 실패했는지 기록하고 진행을 멈춘다.
- 알림 터치·매번 앱 실행·잠금 해제로 대체한 결과를 무터치 목표 달성으로 보고하지 않는다.
- 한국어 온디바이스 인식 또는 연속 발화 처리가 성립하지 않으면, 엔진 대안의 비용·라이선스·오디오 전송 조건부터 검토한다. 승인 없는 클라우드 fallback은 없다.
- 실차의 신선한 안전 상태를 확보하지 못하면 명령을 실행하지 않는다. 성공률을 높이기 위해 안전 조건을 완화하지 않는다.

## 첫 구현에서 만들 것과 만들지 않을 것

**만들 것:** 최소 Compose 진단 화면, 네이티브 서비스 생명주기, 실제 접근 이벤트 수집, 제한 오디오 세션, 호출어·온디바이스 STT 가능 여부 진단, 한국어 TTS 안내, 민감정보 없는 상태 로그.

**현재 만들지 않을 것:** 승인 없는 실제 프렁크 버튼, 상시 STT, 매사용 터치가 필요한 운영 흐름, 안전 상태 미확보 차량 제어, 독자 암호 연산, 차량 상태 주기 폴링 서버. 앱 자체 키·로컬 BLE 등록/읽기·자동 UWB·별도 승인 수동 음성 프렁크는 구현 범위이며 자동 마이크·자동 프렁크는 미연결이다. 초기 기술 검증에서 미뤘던 UI 정리는 사용자 요청에 따라 [별도 개편안](UI-Design.md)으로 다룬다.

## 빌드·실행 상태

현재 소스·APK·S23 설치본은 v66·서비스 OFF다. 최신 관측은 [기기 검증 상태](Device-Validation.md#문서-상태와-대상), 구현 경계는 [자동 UWB와 알림](Native-Architecture.md#홈-자동-uwb-서비스와-복원), 실행 절차는 [빌드 절차](../README.md#빌드와-실행)를 따른다. REA 정적 코드·호스트·USB smoke는 차량 수락·거리·제어 성공의 증거가 아니다.

## 문서 운영과 게시 범위

- 루트의 `wiki/` 폴더가 Wiki 원본이다. 프로젝트 진입점은 [루트 README](../README.md)다.
- Wiki 원본은 프로젝트 저장소에서 관리한다. 커밋·푸시는 사용자 요청에 따라 수행하며, 별도 GitHub Wiki 초기화·웹 게시는 아직 하지 않았다.
- 내부 링크는 저장소에서 동작하는 상대 `.md` 링크를 사용한다. 향후 GitHub Wiki 게시가 승인되면 별도 Wiki 저장소의 페이지 경로에 맞게 링크를 변환하고 실제 게시 화면을 검증한다. 단순 복사로 동기화가 완료되었다고 간주하지 않는다.
- 사실·가설·실기기 결과를 구분하고, 새로운 실험 결과가 나오면 [기술 타당성 문서](Feasibility.md)와 [시험 기록](Device-Validation.md)을 함께 갱신한다.
- 실측 수치는 검증 기록, 현재 구현은 아키텍처, UI 원칙·개편 순서는 UI 검토와 프로젝트 스킬에 둔다. Wiki 홈은 이 자료를 연결하는 요약이며 앱 화면에 시험 문서 전체를 옮기지 않는다.
- 공개 저장소이므로 VIN, Bluetooth 식별자, 계정 정보, 위치, 음성 원문, 토큰·키를 문서나 첨부 로그에 넣지 않는다.
